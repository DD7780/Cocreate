## Conditional same-host alternative

If the guest supports cgroup v2 delegation, retain the existing Worker, image, application and domain. Add only a trusted startup bootstrap and a small fixed browser launcher. Bootstrap creates a bounded execution subtree, enables the required memory/PID controllers, moves the trusted app into its own leaf and delegates only the job subtree to its existing non-root UID, then drops privilege. Neither generated pages nor their mount namespace can see the cgroup filesystem. No Docker socket, host mount or blanket application capability is added.

The trusted launcher configures a fresh random job leaf **before** executing Chromium: proposed `memory.max=536870912`, `memory.swap.max=0`, `memory.oom.group=1`, `pids.max=64`. This proposes physical-memory enforcement in place of the browser's incompatible virtual-address ceiling; it is a policy change requiring an accepted decision and real tests, not an already-approved relaxation. Compiler address/heap limits remain unchanged. Preserve secret-free environment, read-only libraries/job inputs, private namespaces/profile/tmp, no network, 10 CPU seconds, 20-second wall bound and 4 MiB output/file limits. Keep the existing single-process browser contract.

Start a stopped trusted child, place it in the leaf, verify limits/identity and release it only after attachment. Do not race a running browser against parent-side cgroup migration. Parent owns protocol, cancellation and host-visible PID accounting. On timeout/cancel/completion, kill the leaf, wait for `populated=0`, then remove the profile and leaf. Read memory events to distinguish OOM enforcement from unavailable isolation. Missing delegation, controllers, attach/kill authority or startup failure must fail closed. The outer application/container resource bounds remain in force. Linux documentation defines [delegation, hard memory bounds and whole-group kill](https://docs.kernel.org/admin-guide/cgroup-v2.html).

Required evidence: ordinary real browser/compile, secret and cross-workspace denial, live network denial, memory/CPU/output/time exhaustion, cancellation and all-descendant cleanup, no cgroup escape, no application death under job exhaustion, honest previous-artifact retention, full regression suite, then actual Cloudflare kernel preflight and independently authenticated hosted acceptance. CI settings alone cannot prove the guest kernel.

## If delegation is unavailable

Use a disposable job container or microVM with independently enforced memory/PID limits on a supported Linux runtime, reusing the fixed launcher and bounded input/output contract. Keep the coordinator, authentication and private data on their existing services; generated execution receives candidate bytes and approved runtime files only, never Supabase/provider credentials. This introduces an execution boundary and hosting/cost decision, so prepare and approve that explicit decision before provisioning. No migration, new service or reduced-functionality beta is authorized by this design. The existing release remains held while support/capability evidence is missing.
