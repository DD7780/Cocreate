## Conditional same-host alternative

The candidate retains the existing Worker, image/service, application and domain. Trusted startup creates a 1 GiB/256-task common app/jobs subtree, moves itself into an app leaf, enables memory/PID controllers and delegates only job creation/migration to the existing node UID. Aggregate browser jobs are separately limited to 512 MiB/64 tasks. Controller bounds remain root-owned; setpriv drops the app to UID/GID1000 with all capabilities removed. A small parent-death C launcher stops before exec, and the parent attaches/verifies it before SIGCONT. Neither generated pages nor their mount namespace can see cgroup authority, and sandbox capabilities are explicitly dropped. No Docker socket, blanket application capability or new service is added. CI alone binds a dedicated disposable bounded cgroup subtree; its four narrowly scoped bootstrap capabilities are dropped before any app/test code.

Each fresh random browser leaf is configured and verified **before** executing Chromium: `memory.max=536870912`, `memory.swap.max=0`, `memory.oom.group=1`, `pids.max=64`. D-0057 records the implementation direction under the user's supported-isolation repair request; release still requires actual tests. This replaces the browser's incompatible virtual ceiling with physical enforcement rather than raising an address-space limit alone. Compiler address/heap limits remain unchanged. Preserve secret-free environment, read-only libraries/job inputs, private namespaces/profile/tmp, no network, 10 CPU seconds, 20-second wall bound and 4 MiB output/file limits. Keep the existing single-process browser contract.

Start a stopped trusted child, place it in the leaf, verify limits/identity and release it only after attachment. Do not race a running browser against parent-side cgroup migration. Parent owns protocol, cancellation and host-visible PID accounting. On timeout/cancel/completion, kill the leaf, wait for `populated=0`, then remove the profile and leaf. Read memory events to distinguish OOM enforcement from unavailable isolation. Missing delegation, controllers, attach/kill authority or startup failure must fail closed. The outer application/container resource bounds remain in force. Linux documentation defines [delegation, hard memory bounds and whole-group kill](https://docs.kernel.org/admin-guide/cgroup-v2.html).

Required evidence: ordinary real browser/compile, secret and cross-workspace denial, live network denial, memory/CPU/output/time exhaustion, cancellation and all-descendant cleanup, no cgroup escape, no application death under job exhaustion, honest previous-artifact retention, full regression suite, then actual Cloudflare kernel preflight and independently authenticated hosted acceptance. CI settings alone cannot prove the guest kernel.

## If delegation is unavailable

Keep the coordinator, authentication and private data on their existing services; generated execution receives candidate bytes and approved runtime files only, never Supabase/provider credentials.
