An explicit subsequent build with repaired behavior promotes successfully.

Validated operations and isolated compilation precede the role-gated `project.verify` tool. The parent selects fixed checks from frozen eligible accepted criteria, runs generated browser code in the Step 04 OS boundary, and owns assertions and hashes. `candidate.verification_recorded` is durably saved before publication. `project.promote` independently rejects missing, stale, inconsistent or failed required evidence before workspace writes. Existing frozen specification/fingerprint, intent-commit and coordinator ownership fences remain around upload and commit. Model outputs, generated test files and HTTP input cannot select checks or supply promotion context.

Evidence binds specification revision, requirement ID/revision, criterion hashes, full source and compiled JS/CSS candidate hash, plan and check version (`list-behavior-v1`), check time and browser version. Requirement rows distinguish observed/missing/unknown implementation and verified/failed/unverified status. Observed means the required control/list was found, not proof of the entire feature. A compiling behavioral failure retains `operationsApplied=true`, `compilationPassed=true`, failed satisfaction/regression evidence and the prior artifact. Reports persist in run/version snapshots; source inspection confirms existing private archive metadata preserves `aiRun`. Existing recovery tests run in the required suite, but no live hosted report-restoration test is claimed.

Every candidate reruns all retained covered behavior; it cannot borrow an old report. Changed source, compiled CSS, specification/requirement revision, criteria, plan or policy invalidate evidence. The unchanged-fingerprint shortcut also requires current source/compiled evidence for covered behavior, so legacy compile-only records cannot bypass new checks. Old records remain honestly unverified. Attribution-only reuse of an existing artifact does not fabricate a new evidence revision.

Byte-identical source may reuse compiled bytes from the available version only after this coordinator instance itself completed and durably promoted that compilation. A private `WeakSet` supplies that provenance; matching source and full compiled hashes are also required. Reloaded/legacy records or changed bytes require real isolated compilation. `build.compilation_reused` records the source version and current candidate hash/revision. This avoids redundant compilation without reusing functional evidence: every candidate still runs fresh browser checks for its frozen accepted revision, and boundary preflight still precedes builder dispatch.

## Deliberately bounded coverage

The grammar strips the existing `A user can verify this behavior in the product:` wrapper, ignores case and one terminal period/exclamation mark, and supports these exact families:

- Build/Create a catalog, recipe catalog, recipe list or list with a filter/search, optionally described as working/functional.
- Add/Include/Enable/Support favorites/favourites, optionally toggle/toggles.
- Add/Enable/Support sorting, optionally alphabetical and/or by name.

Other prose remains unverified, including combined requests outside that grammar. There is no LLM-generated assertion policy or claim of complete semantic correctness. The builder receives the observable contract without authority to change it: a visible semantic list (`ul`, `ol`, `role=list`, `tbody`, or articles), item titles and at least two representative entries; accessible labeled search/filter input or select; favorite button with pressed state or checkbox; accessible alphabetical sort button/select.

Filtering must narrow to matching item names and restore after clearing; selects must narrow and restore. A favorite state must toggle and restore without removing entries. Sorting must change into alphabetical order without losing entries. Separate browser targets dispose the previous React runtime and DOM world for each check. These bounded DOM interactions do not prove persistence, every item/variant, arbitrary prose, absence of unsolicited features, adversarial semantic equivalence or live provider quality. Uncovered criteria may promote with explicit unverified coverage; full verified status requires all frozen criteria to be covered and pass.

Functional failures stop without automatic provider repairs. Existing operation/compilation repairs remain bounded at two BYOK attempts, at most three compatibility attempts and the shared 24-physical-dispatch ceiling. Explicit retry/new steering is required. No model, credential, provider or funding fallback was added; durable workflow budgeting remains Step 08.

## Isolation and operator setup

The Windows launcher adds browser mode under the same zero-capability AppContainer and suspended-before-Job-Object assignment. The browser has a job-scoped writable profile, stripped environment, no network capability, one-process limit, 512 MiB process/job commit limit, 10 CPU seconds, 20 seconds execution wall time, 4 MiB protocol output and bounded diagnostics. Parent-controlled CDP uses inherited anonymous pipes; DOM assertions run in a separate isolated JavaScript world with pristine prototypes. That world protects assertion code from page prototype replacement; the OS boundary remains mandatory.

The headless shell uses one process and disables its internal Chrome sandbox to fit the external one-process boundary. This does not replace or relax the AppContainer/Job Object restrictions. The parent terminates completed work through the native cancel/job path, waits for exit, and removes its UUID job/profile; it does not rely on generated code or browser shutdown to clean up. Cancellation/resource failures remain fail-closed. Native exit/peak-commit diagnostics contain bounded numeric metadata rather than environment, prompts or page contents.

Installed branded Chrome failed crashpad initialization in the AppContainer; [first](../../artifacts/multiuser-step07/browser-boundary-probe-first.log) and [second](../../artifacts/multiuser-step07/browser-boundary-probe-second.log) probes remain failed evidence. Official Chrome-for-Testing headless shell **154.0.8037.92** passed the [contained probe](../../artifacts/multiuser-step07/browser-boundary-probe-shell.log). Windows operator setup is `./scripts/prepare-verification-browser.ps1`: pinned official download, SHA-256 validation of ZIP and executable, then an inference-free actual boundary preflight. Existing runtime binaries stay ignored. Builds never download a browser or silently select the host installation. Covered work preflights the selected executable before builder spending; changing the executable invalidates cached readiness.

Linux Docker preparation installs Chromium and keeps Bubblewrap/prlimit isolation, scoped profile, cleared environment and the existing resource limits. **Actual Linux namespace/browser/address-space/runtime acceptance is unrun and required before release.** Run `pnpm exec tsx scripts/prepare-verification-browser.ts` in the intended runtime and complete adversity checks; unavailable/incompatible execution stops before covered builder dispatch. No image, deployment, SQL migration, hosted account, live provider or paid inference was exercised.

Implementation references: [CDP Target](https://chromedevtools.github.io/devtools-protocol/tot/Target/), [CDP Page isolated worlds](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-createIsolatedWorld), [Chromium inherited Windows pipe handles](https://chromium.googlesource.com/chromium/src/+/lkgr/content/browser/devtools/devtools_agent_host_impl.cc), and [Windows job accounting](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject).
