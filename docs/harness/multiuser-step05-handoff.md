## Durability, uncertainty and compatibility

Intent commands and conflict commits share the steering queue. The server rechecks current membership/ticket expiry and coordinator authority at execution, and checks expected specification/target revision. Pending intent projects the prior accepted state to readers, defers competing snapshots/promotion and acknowledges only canonical save success. A lost/failed canonical reply permanently fences this local instance; it never compensates against possibly committed remote state. Recover a coordinator from canonical storage and replay the same request ID: committed commands return one receipt, absent commands may be applied once against the restored revision. The controlled lost-reply test establishes that protocol; it does not execute real hosted SQL. In-memory drafts and concurrent participant state are preserved on rollback; device request-copy failures remain visible.

Snapshot fields are additive: interpretationHistory, intentCorrections, intentReceipts, intentBuildPending, submission intentContext and per-intent/source validation/authority/reference metadata. No SQL migration/schema change or historical compaction. Readers must retain receipts/history on write. Drain writers and preserve these fields before app-only downgrade; an older writer dropping them breaks replay/history. Both coordinator migrations and hosted rollout prerequisites from Steps 02/03 remain prepared/unapplied.

Public `/process` and `/reinterpret` return authenticated HTTP 410 and no inference. The internal legacy diagnostic is serialized/fenced, uses recorded caller edits with accepted context, independently validates output and awaits persistence; settled decisions/withdrawals still require new human correction. It is not a public correction/funding surface. Existing local direct harness helpers remain trusted test/compatibility methods, not model-selected tools.
