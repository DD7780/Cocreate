# Role-compatible OpenRouter models

## Change packet — 2026-10-16

Outcome: the user reports a Build my changes failure, possibly output- or credit-related and requests only suitable choices for Builder and Interpretation, with unmistakable free pricing. The current catalog puts the same models in both roles, admits unknown completion limits and JSON-mode-only models, and silently lowers role allowances. Setup must remain inference-free; owner/editor funding and caller-only submission remain unchanged.

Scope: `server/byok-lease.ts`, `server/rooms.ts`, `server/providers.ts`, `server/generator.ts`, `shared/types.ts`, `src/ByokSetup.tsx`, focused model/provider tests and affected canonical documentation/release metadata. Server/shared changes are necessary because hiding options alone cannot enforce valid model assignments or provider routing. No database, membership, receipt, coordinator, physical-attempt, recovery-task or spending-limit changes.

Evidence: Graphify query `OpenRouterLeases modelsFrom saveTemporaryModels model context output limit bigger larger builder personal` locates the lease, assignments, adapter, generator and managed-AI tests. Source confirms identical role lists, a 16,000-context filter with optional output metadata, role caps of 8,000/2,400 and a generic two-exhaustion error recommending a larger model. The actual failing model/request is still unknown; these are verified selection/request defects, not proof of the user's particular provider outcome.

Contracts: require text input/output and advertised JSON Schema support (`response_format` plus `structured_outputs`), valid published pricing, a known positive completion ceiling and adequate context for each role. Builder needs at least 64,000 context / 16,000 output; Interpretation needs 32,000 / 8,000. Save only exact IDs from the appropriate list, with those disclosed role response ceilings (the recovery manifest remains capped at 2,000) and existing input headroom. Unknown capacity is excluded. Reasoning models must advertise a supported lower effort (low, otherwise minimal; null supported_efforts means all gateway efforts are supported), or explicitly optional reasoning which is disabled; unsupported/unknown mandatory reasoning is excluded. The setting is displayed and frozen with assignments, then reaches interpretation, builder and file recovery. Low effort is guidance within the hard response limit, not a guaranteed reasoning-token allocation. OpenRouter structured calls require supporting endpoints and cannot silently drop the schema. Free means all reported price components are explicitly zero, with required prompt/completion rates present; paid choices show input/output USD per million and any request fee. Catalog eligibility is distinct from successful paid quality testing and provider availability. No generation probes run on connect/save.

User subsequently identified Kimi K3 for interpretation and “open muse” for Builder, then clarified the error may have said smaller rather than bigger model. Current catalog matches `moonshotai/kimi-k3` (default-max optional reasoning) and likely `meta/muse-spark-open` (mandatory reasoning, low supported); this does not identify the exact failing request. A credit/affordability failure is also possible. Credit errors now retain bounded provider details and suggest checking key credit/quota or choosing a free model, without automatic retries or model substitution.

Current official evidence: [structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs), [provider routing](https://openrouter.ai/docs/guides/routing/provider-selection), [model metadata](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties), [reasoning and response limits](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens). Anonymous catalog retrieved 2026-10-16 contains 465 models; counts are observations, not a pinned recommendation list. Reasoning can consume completion allowance, so filtering cannot guarantee unlimited builds. Retain bounded recovery and make exhaustion advice describe the actual request limit rather than imply that a model switch necessarily raises it.

Verification: regression tests must first demonstrate the current eligibility/pricing/routing defects, then pass. Run managed-AI, providers, build recovery, workflow budget and submission regressions; boundaries, full suite and production build; controlled browser checks for both dropdowns, free/paid groups, selected prices, role exclusions, phone layout and inference-free save. Preserve unrelated dirty Graphify outputs; refresh graph after source edits. Live provider quality/accounts and billing remain untested without a designated key/budget.
