## Durable authority and storage

A project maps to one room and one durable workflow. Browser state, model memory and summaries are projections, not authority. The local mode stores ordered append-only SQLite events with workspace sequence, actor, input revision, hash and artifact reference, plus derived workspace/run/workflow/task views. Artifacts are content-addressed. Legacy JSON is backed up before lazy import and compatibility writes remain. Restore interrupts nonterminal runs/tasks and moves the workflow to awaiting input without repeating provider side effects.

Hosted Supabase Auth supplies identity; Postgres supplies project/membership and canonical snapshot/update/usage authority. SQLite/JSON is cache/local mode and must not silently take authority on hosted failure. The implementation embeds `events`, `workflow_state`, `task_state` and `run_state` in `project_snapshots.harness_state.harnessProjection`; it does not currently use every separately declared hosted harness table as a normalized live projection. Restore validates workspace IDs and replaces these local projection rows transactionally.

Snapshots retain pending participant edit batches, active submissions, permanent participant/request receipts, accepted revision snapshots, current checkpoint metadata, the current six version descriptors, permanent archived-version metadata, recent 50 AI runs and retained provider records. The hosted physical-call ledger is a broader separate record source. `server/artifacts.ts` defines deterministic product/checkpoint envelopes; private Storage objects live at `<projectId>/bodies/<sha256>` with `upsert:false`. Publication verifies uploaded or already-existing bytes, caches verified immutable publications within the process, rechecks coordinator authority and then commits references using the existing fenced canonical snapshot RPC. The active pipeline uses `harness_state.artifactSchemaVersion=1`, manifest and history, rather than the unused compatibility ZIP `artifact_versions` reservation method. No new SQL migration is introduced; the original bucket policies and coordinator migrations were observed applied on 2026-10-08; real Storage replacement and coordinator contention remain prerequisites.

Current product bundles/files and the relevant candidate checkpoint are hash/length verified and materialized before hydration into an empty derived cache. Project/kind/version identity and source paths/content are checked; legacy partial source archives remain readable without claiming they compile. Older archived versions and other non-workspace event bodies are retrieved on demand through the same verified manifest. Exported events carry references; publication additionally gathers their non-workspace bodies. Historical full workspace-snapshot bodies are deliberately excluded from recursive archival, while the canonical current snapshot and event projection remain authoritative. Legacy inline snapshots are readable and their available bodies are archived on a subsequent save; versions already discarded beyond their former six-version window cannot be recovered. Corrupt/missing required data fails opening explicitly and never silently creates an empty room or starts inference.

Before promotion the candidate body is published, then ownership/revision/fingerprint are rechecked. Until canonical commit, the candidate is excluded from preview/version state and concurrent autosaves wait. Publication/commit failure rolls back to the previous product, clears the pending gate and preserves later edits; ownership loss cannot authorize promotion. Immutable version IDs increase beyond retained history even after rollback. Interrupted uploads may leave private unreferenced bodies; replay verifies and reuses them without duplicate inference. Current membership and coordinator checks run again after awaited historical reads before response bytes. No public/signed URL is created.

Full projections, permanent receipts, version metadata and private objects still grow. The synthetic 0/10/50 version+receipt sample measures snapshots of 1,646/18,901/83,748 bytes, with exactly one upload per body in the fixture process. This is not production capacity evidence. Proposed compaction separates permanent request receipts/physical outcomes, uses verified projection checkpoints plus append-only event tails and keeps artifact manifests; cursor/replay/recovery guarantees require review before any cleanup. No historical migration, pruning or object deletion is implemented. Real Storage/RLS, real SQL contention and deployed disposable-container tests remain unrun.

Yjs V1 updates are written as explicit PostgreSQL hex bytes. Restore validates in an isolated document. The exact legacy Node Buffer JSON envelope is accepted only through strict decoding with original-byte quarantine; snapshot recovery uses individually valid updates matching stored SHA-256. Decoder guessing or destructive replacement is not permitted.

## Edits, submission and acceptance

1. Authenticated socket edits apply to Yjs and create participant-attributed edit records. Presence/awareness is ephemeral. Edits schedule persistence, not inference.
2. Browser updates coalesce for 40 ms. Submission drains them, requests flush, and waits for ordered document writes plus a canonical snapshot. Flush failure prevents the HTTP submit.
3. `submitChanges` checks the authenticated participant, temporary spender authority and request replay. It captures a structured clone of that participant's pending batch, frozen models/setup, document revision and accepted-registry context. It removes only that batch from pending and saves before interpretation.
4. All nonterminal submissions survive the recent terminal-history cutoff. Receipts keyed by `[participantId, requestId]` protect replay beyond that cutoff. Empty/replayed commands do not consume new edits.
5. A room steering queue interprets captured submissions in capture order. The primary submission path sends the complete authenticated edit batch and accepted baseline, without teammates' raw unsubmitted canvas context or the old edit clipping. Oversized input fails visibly.
6. Personal outputs classify each intent and reconcile attributable sources into stable requirements. Explicit requests/decisions become accepted; proposals/questions/ambiguity stay visible. Persistence failure rolls back acceptance and restores the author's batch. Interrupted interpretations restore captured edits for explicit resubmission.
7. Nearby eligible accepted changes use the configured build collection window. At its deadline, admission closes even with queued interpretations; at most the already executing interpretation finishes. Later wrappers skip inference. The queue tail freezes eligible requirements/revision/fingerprint and starts one builder. Subsequent submissions persist captured batches without joining the blocked steering queue, allowing explicit correction/conflict commands to invalidate affected work. After success, held captures reconcile serially for the next bounded collection; after stopped/failed work they return to author drafts for explicit resubmission without inference (D-0049). No stale candidate is promoted.

Step 01 historically reproduced acceptance of unresolved “that” and invented passages. Step 05 adds independently checked captured-source and known-context-reference validation, including owned insertion fragments and shorter replacements. Unknown sources/targets remain visible ambiguity rather than accepted builder input. This is scoped provenance/reference enforcement, not proof of complete semantic correctness. Public legacy reinterpretation is retired; its internal diagnostic uses captured author edits, attributed accepted context and serialized owner checks. Automatic restart resumption is not implemented: restoration is inference-free and awaits human action. See the Step 05 boundary below.

Deletion is not withdrawal. Conflict groups hold stable subject/scope, alternatives, contributor set, group revision/round, selections and decision history. The authenticated selection route checks current editor/owner membership AND affected contributor, revision/timestamp and request ID, serializes choices and awaits persistence. Silence stays pending; disagreement retains options; unresolved requirement IDs are excluded while independent accepted work remains eligible. Detection is deterministic for known structured cases, with coarse dependency scopes; broad semantic detection, document highlights and richer compromise/reopen UI are incomplete.

Step 09 retains this serial queue (D-0052). Its offline two-worker experiment receives reversed completions but reconciles in capture order in memory; it is not a durable completion/recovery implementation. The shared-batch experiment uses the existing intent schema and independent per-capture stamping/source validation, with synthetic attributed results. Neither is a production dispatch path. Actual queue/SQLite observations preserve completed queued interpretations and restore deferred uninterpreted captures to failed receipts plus author drafts without inference. Fresh authority failure lets the next authorized capture proceed without poisoning the steering queue. Provider I/O has existing bounded retries/timeouts; persistence and authorization waits are separate, so no overall queue latency SLA is claimed. See the [Step 09 handoff](multiuser-step09-handoff.md) for measured tradeoffs and unresolved native publication observations.

## Coordinator and immutable saves

The exported server `stop()` closes HTTP ingress immediately, terminates sockets and awaits in-flight HTTP responses before disposing RoomManager/SQLite and the hosted coordinator. This avoids reconnect/read handlers observing a closed database during explicit replacement; it does not change takeover epochs, author permissions or automatic inference, or establish deployed signal/abrupt-termination behavior.

Local coordinators use SQLite owner/epoch/expiry leases for processes sharing that store. Hosted `RemoteCoordinator` coalesces claims/renewals, bounds each RPC to five seconds and validates positive safe-integer epochs. Ten-second heartbeats renew a thirty-second database lease. A failed renewal permanently invalidates that process for the workflow, including delayed results and closed coordinators. Loss notifications cancel save/build/agent timers, abort controllers and close sockets with 1012. Fresh checks after durable dispatch accounting and immediately before promotion prevent old workers from proceeding when loss is observed. An already-dispatched external request cannot be undone; outcome reconciliation remains distinct from permission to dispatch.

The prepared original coordinator migration and additive `20261003203000_coordinator_dispatch_updates.sql` use one project transaction advisory lock followed by the lease row lock. Snapshot commits, document appends and dispatch intents recheck owner/epoch/expiry after locking. Equal-revision snapshots and same-sequence updates permit exact replay and reject conflicting bytes/JSON even when claimed hashes match. SQL 40001 invalidates local ownership. Final physical-call reconciliation can still record external outcomes without authorizing a new dispatch. Invoker functions have a blank search path and service-role-only execution grants. Both coordinator migrations were observed applied on 2026-10-08 with matching repository function bodies; real contention/takeover acceptance is pending.

The existing Worker targets the stable `primary` container with one configured instance. This affinity plus bounded retry is the chosen smallest routing policy (D-0045). Membership is checked before ownership on HTTP and WebSocket ingress, even before room hydration. Non-owners return redacted HTTP 503 with Retry-After 2; there is no forwarding or redirect of tickets, keys or bodies. The client bounds diagnosis to three seconds and retries connection at most six times, with owner delay clamped to 2-10 seconds. Exhaustion presents a reopen action and retains page edits. Commands keep caller/request identity; reconnect does not POST submissions. Future scaling requires explicit deployment/database verification.

Each save captures its revision, timestamp, Yjs insertion vector and deletion-range signature alongside an immutable clone. The persist queue serializes remote commits. Only the committed snapshot's receipt is sent as saved; errors remain unsynced. Ordered update append failure may recover through a confirmed full snapshot; snapshot failure cannot be called saved. Local SQLite completion cannot acknowledge Postgres.

Within a socket generation, the browser rejects older workflow/snapshot cursors and save revisions. A new authenticated connection resets these cursors and accepts its first canonical state, including a lower cursor after failed prior writes. Saved status requires the receipt to cover both local insertions and deletions. Device-saved status follows a separate IndexedDB transaction. Cache keys include room and participant, bytes are validated before merge after authenticated state, and quota/corruption errors are visible. Full offline cold startup and account purge/retention controls are incomplete.

Hosted reads/mutations, preview/download access, socket upgrade, received messages and outbound packets recheck membership; current role limits viewer writes. Socket tickets expire after five minutes. Revoked members receive no later delivery after the delivery check, but there is no proactive push closing every completely silent idle socket immediately. This distinction and per-delivery query cost remain relevant.

## Candidate generation, recovery and promotion

The shared builder receives accepted eligible requirements and bounded project files, never raw canvas as authority. Changed/removed requirements are compared with the last promoted baseline. It applies validated room-scoped operations through typed tools, compiles, then promotes only if revision/fingerprint and ownership still agree.

Hosted BYOK uses requested builder/interpreter outputs of 8,000/2,400 before lower reported completion/context caps; effort is not proof of a higher provider ceiling. Complete input sizing remains conservative bytes rather than provider tokenization. Omitted-file names are available but full model-aware retrieval/references remain incomplete.

Whole-project output exhaustion skips the repeated oversized retry and requests a schema-constrained manifest of one to eight ordered one-file tasks. Each task returns exactly one complete write at the planned path, passes operation validation and awaits a durable checkpoint before continuing. Whole JSON envelopes are not resumed by concatenating truncated text. Checkpoints are source candidates; an explicit retry may reuse them only for the same accepted fingerprint.

`server/workflow-budget.ts` owns physical admission and settlement; each room serializes accounting mutations, not inference, through an accounting queue. The durable workflow scope starts on its first authorized physical interpretation/build dispatch and includes generation, smaller-task recovery, structured/compilation repairs and transport retries. It allows 24 attempts; measured outcomes reconcile the original reservation once, while unknown/incomplete outcomes retain the conservative reservation and explicit uncertainty. Attempt IDs never replenish. Retry, supersession, cancellation, model/key reconnect and process restart keep the scope. A successful fully drained cycle closes it durably; a later explicit submission/build opens the next cycle. An idle owner can explicitly reset the scope with its expected ID and permanent actor/request-ID receipt; reset itself performs no inference. Old scope records and uncertainty remain in the ledger. Interrupted legacy snapshots without a durable allowance fail closed and require that reset. Setup operations have separate named scopes with a 24-attempt bound, never silently consume the workflow allowance, and have no new dollar-budget UI. Frozen configured spending and provider account limits remain separate; hosted BYOK funding is unchanged. Snapshot state retains the current scope, attempts and reset receipts. Before HTTP, the coordinator saves the scope plus reservation/event projection, awaits the physical-ledger dispatch acknowledgement, then rechecks ownership and current membership/funding. Save uncertainty permanently fences the coordinator. The full hosted/local ledger repairs snapshots that predate reported outcomes, deduplicating attempt IDs; confirmed measured outcomes cannot be downgraded by delayed intent/unknown reports. No new SQL/schema or migration is introduced: existing fenced snapshot/dispatch RPCs remain mandatory rollout prerequisites.

Compile/repair attempts remain bounded (two for temporary BYOK, at most three for compatibility configurations) within the shared physical bound. Source/path validation, tool policy, revision and lease gates protect integration. Failed candidates retain the last compiled preview and include recovery/task/call information plus a next action. Compilation alone records unverified functional evidence; Step 07 now additionally gates covered criteria on trusted browser checks. Runtime error reporting can restore the previous version; there is no general rollback/control API.

## Step 05 intent authority and commit boundary

`server/intent-authority.ts` validates provider output against authenticated captured edits and the frozen attributed accepted context stored with each submission. Offline Jev dispatch selects direct TypeSafe or Vercel explicitly with separate credential variables and fixed endpoints. Vercel's TypeSafe-compatible route uses `typesafe-ai/jev`, an unpinned gateway alias; direct calls retain `jev-1.13.0`. Provider/endpoint fingerprints isolate caches, gateway aliases expire after 24 hours, and gateway-reported costs are distinct from token estimates. There is no automatic retry, credential crossover or provider/model fallback. The 20-file Vercel smoke run is recorded in [cleanup verification](codebase-cleanup-verification.md).

The cleanup moves contracts and pure helpers without changing request/event shapes or coordinator authority. Historical managed accounting/catalog modules remain for compatibility, tests and persisted data; inactive UI does not prove the corresponding storage contracts are removable.

## Requirement-linked candidate verification (Step 07)

server/verification.ts maps a deliberately narrow accepted-criterion grammar to fixed filter/favorites/sort checks. Unmatched prose is unverified rather than a guessed assertion. The builder receives the semantic list/control contract, but no ability to choose policy. Validated operations and isolated compilation precede the audited project.verify tool and browser observation; all eligible retained covered behaviors are rerun per candidate. Byte-identical source can reuse available compiled bytes only with this coordinator instance's successful durable-promotion provenance and matching source/compiled hashes. A private WeakSet supplies that provenance; persisted or legacy reports alone cannot. The build.compilation_reused event identifies the source version and current candidate revision/hash; functional evidence is always regenerated. Filtering must narrow by a distinct item-name query and restore; favorites must toggle and restore pressed/checked state; sorting must change alphabetical order without item loss. Each check uses its own browser target with the existing CSP/storage bootstrap. These are bounded observable checks, not arbitrary semantic proof or generated tests executed with authority.

CandidateVerification records source/compiled candidate/plan hashes, accepted specification revision, requirement revisions/criterion hashes, check version, browser version, observed/missing/unknown implementation and verified/failed/unverified coverage. candidate.verification_recorded is appended and durably saved before artifact upload/promotion. Run/version metadata retains the report through snapshots and private archive envelopes; no new SQL or parallel progress ledger is introduced. project.promote independently rejects absent, stale, inconsistent or failed required evidence, before workspace writes. Existing lease/fingerprint/intent gates remain around upload and commit. Failed behavior preserves compilationPassed=true where applicable and the prior artifact; it stops without provider repairs. Uncovered criteria may promote explicitly unverified. Unchanged-fingerprint reuse requires current recorded evidence for covered behavior; legacy records remain honestly unverified.
