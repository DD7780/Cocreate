# Build my changes recovery

## Change packet — 2026-10-16

**Outcome.** The owner or an invited editor clicks Build my changes, or uses editor-focused Alt+X. A slow or rejected save currently ends the action silently; a later click after a recorded submission failure only replays the failed receipt. Show saving/submitting progress and actionable failures, allow a bounded 15-second canonical-save wait, and let an explicit retry recover the old receipt before creating a fresh submission when that receipt confirms failure.

**Scope.** Client behavior only: `src/App.tsx`, `src/provider.ts`, new `src/submit-changes.ts`, submission/provider regressions, this packet and affected canonical steering. Release-input manifest/fingerprint updates are required by the existing image guard. No server, shared contract, SQL, permission, key lifetime, provider-selection or inference-on-typing change. Preserve unrelated dirty Graphify files.

**Evidence.** Graphify query `submitChanges CoCreateProvider flush commandReceipts failed submissions api client` locates `RoomManager.submitChanges` in `server/rooms.ts`. Source verifies the three-second flush deadline (`src/provider.ts`), empty client catch (`src/App.tsx`), and permanent failed receipt replay (`server/rooms.ts`). The 2026-10-16 investigation reproduced silent save failures using the current callbacks/provider and the extra-click retry using the real RoomManager with a loopback fixture. The live client contained the same timeout and empty catch. The user reported: “Nothing happened, it just went away.” Production save latency and the exact affected project's receipt remain unverified.

**Required contracts.** Flush must succeed before any submission POST. Only the authenticated caller's pending edits are captured. Unknown HTTP outcomes retain the same request ID; successful replay never consumes newer edits. Only a confirmed failed receipt may release the old request ID for one fresh submission during the next explicit click. Bound this recovery to one fresh attempt; no automatic inference retry after that attempt fails. Keep current owner/editor/viewer and BYOK spender checks, durable capture order, one coordinator, serialized promotion and retained artifacts. No `shared/types.ts` or HTTP/WebSocket schema changes.

**Verification plan.** Test delayed acknowledgement beyond three seconds, actual save rejection, timeout/disconnect, positive progress, no POST before save, request-ID preservation after uncertain outcomes, successful receipt replay without new capture, and failed-receipt recovery for owner/editor paths using controlled fixtures. Run focused regressions, strict production build, boundaries, UI scope audit and AST-only Graphify update. Attempt the full suite; distinguish the documented unavailable local verification-browser failures from new failures. Browser claims require browser evidence; hosted accounts, private logs and live paid inference remain separate acceptance.

## Implementation and evidence

- `src/submit-changes.ts` now owns save/submission progress, errors and bounded receipt recovery. The button and shortcut use this same helper. A save rejection/timeout clears progress, shows the actual error and sends no submission. New save timeouts explain that no build started. Focus restoration avoids an already-destroyed editor.
- The default flush deadline is 15 seconds. This accommodates the reproduced 3.3-second save while preserving an acknowledged save before POST. This is a bounded tolerance, not proof of a particular production database bottleneck or a guarantee against every slow save.
- A later explicit click first replays an uncertain request ID. Only a failed receipt permits one fresh submission in that click. A lost successful reply replays without consuming newer edits or spending again. Another failure stops, retaining the new ID if its outcome is uncertain.
